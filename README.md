# gtr9-postboot-log-analysis

**Version 7.14.0** · [Changelog](CHANGELOG.md)

Builds a PDF report from a `cachyos-bugreport.log` and a ry-verify JSONL log: the findings with their evidence and the commands they call for, system health, the boot, dmesg, the journal, and the ry-verify results. Every finding, quote, count, and figure comes from the two inputs on each run; the script holds analysis rules, never results.

## Quick Start

```fish
sudo pacman -S --needed python-reportlab python-matplotlib python-svglib python-pillow ttf-ibm-plex
chmod +x build_report.py
sudo cachyos-bugreport.sh
~/ry-verify/ry-verify.fish --verify
./build_report.py --bugreport cachyos-bugreport.log --verify (path sort ~/ry-install/logs/*/verify-*.jsonl)[-1]
```

- Run the steps in the directory that holds `build_report.py`. `chmod +x` restores the executable bit a download or a copy can drop; without it fish answers "exists but is not an executable file".
- `cachyos-bugreport.sh` must run as root, writes `cachyos-bugreport.log` to the current directory, and then offers to upload it; answer no.
- `~/ry-verify/ry-verify.fish` is where the clone command in ry-verify's README, run from the home directory, puts it; it logs to `~/ry-install/logs/<date>/`.
- `path sort` picks the newest ry-verify log by its timestamped name; `ls -t` fails there, as CachyOS's fish config makes `ls` an alias for `eza`, which reads `-t` as `--time`.
- The PDF lands in the current directory as `post-boot-log-analysis-<capture date>.pdf`, which a later run on a same-day capture overwrites; its absolute path is printed on stdout.
- `uv run build_report.py …` (pacman: `uv`) installs the dependencies listed at the top of the script instead and needs no executable bit; the fonts still come from `ttf-ibm-plex`.

## Inputs

- `--bugreport PATH` — required; the log `cachyos-bugreport.sh` (CachyOS-Settings) writes, with its header, inxi, scheduler, dmesg, both journal boots, and package list
- `--verify PATH` — required; the JSONL log of a ry-verify `--verify` run (`verify-*.jsonl`) under `~/ry-install/logs/<date>/`; a `--check` log holds no results and is refused

## Usage

- `--out PATH` — output PDF; default `./post-boot-log-analysis-<capture date>.pdf` (the ry-verify start date when the bug report states none, else `undated`), with `-brief` before `.pdf` under `--brief`; the PDF and the JSON summary are written to scratch files beside their targets, created exclusively under unpredictable names, then renamed over them, and get the permissions a new file gets there, from the umask or the directory's default ACL
- `--brief` — the cover and Sections 1 to 3 only, about six pages for paper; a reference to a later section names the full report, and the PDF's title says brief
- `--json PATH` — also write the findings as a JSON summary (below), replaced in the same step as the PDF
- `--compare PATH` — an earlier run's JSON summary: the register gains a Change column (new, worse, better, or same; findings match by rule, ry-verify findings by status, phase, and section, and one that was INFO is new), a line under it names the findings resolved since (gone, or lowered to INFO) by title and earlier ID, the verdict counts the new and the resolved findings, and a summary from another machine is named as such; while this run's ry-verify log comes from another boot or machine, the earlier run's ry-verify findings are counted as not compared, not as resolved
- `--no-attach` — leave the two inputs out of the PDF, which otherwise carries them byte for byte, identifiers unmasked, as file attachments (`pdfdetach -list`); use it for a PDF that goes to someone else
- `--fonts DIR` — directory with the 9 IBM Plex TTF files; default search `/usr/share/fonts/TTF`, `/usr/share/fonts/truetype/ibm-plex`, `$XDG_DATA_HOME/fonts` (`~/.local/share/fonts` when unset or relative)
- `--check` — run the preflight, parse both inputs, and run the parser cross-checks, then stop; its report on stderr counts journal lines the parser could not read and names any cross-check that differs
- `--verbose` — report on stderr the setup (the font directory and the Python and library versions), then for a build the parse, the `--compare` summary, the analysis, where a ry-verify log from another boot or machine comes from, the charts, each layout pass, and each file written
- `--version`, `--help` — version and usage; both work before the Python dependencies are loaded

## Exit Codes

- `0` — built, or the inputs parsed under `--check` (a differing cross-check is reported, not an error)
- `1` — build or check failed: an input in the wrong format (a ry-verify log of another mode among them), a `--compare` file that is no summary, an unsettled layout, an unresolved page reference, or an output that cannot be written: a directory that takes no new file, a default PDF name that names an input, a directory, or no regular file, or a `--json` path that is the PDF. When the summary fails after the PDF has replaced its target, the message names the PDF
- `2` — usage error: a missing `--bugreport` or `--verify`; an unknown option; `--out` or `--json` naming a directory, anything else that is not a regular file, or one of the inputs (also through a link); `--check` with `--brief`, `--json`, or `--compare`; or a `SOURCE_DATE_EPOCH` that is not a whole number of seconds up to 253402300799 (9999-12-31)
- `3` — preflight failed: a Python module, a font file, or an input file is missing or unreadable, an input is no regular file (a pipe or a device), or a font file is no TrueType font; the message names why
- `130` — interrupted with Ctrl-C, `SIGTERM`, or `SIGHUP`; nothing is written, unless the PDF had already replaced its target, which the message names. A signal after the run is over leaves its exit code. A signal while Python itself starts, before the script runs, is Python's to handle: Ctrl-C prints `KeyboardInterrupt`, and `SIGTERM` or `SIGHUP` ends the process

## The Report

- **Cover** — the verdict; counts of findings by severity, watch items, dmesg lines and journal entries, and ry-verify FAIL, WARN, and GEN_FAIL, in one type size that fits the widest; tiles for the error classes, boot to root mount, unit failures, GPU memory, and temperatures, as far as the inputs state them; the uptime strip, in seconds since kernel start on a log scale: the boot phases, where each bug-report finding that calls for action first shows, the ry-verify run (a diamond), and the bug report (a square); a finding's label stands above the ticks it reaches and clear of the labels it would meet, labels that reach each other's ticks merge, two capture labels that would meet share one, and the capture labels stand a row below the phase names when one would meet a name; a capture within 0.1 s of the kernel start is marked at the strip's left edge; and the action checklist with the findings each action answers and its completion test.
- **Contents** — sections and figures with their pages, a reading guide, and the severity levels.
- **1 Summary** — key facts and the register of findings that call for action.
- **2 Findings** — a card for each bug-report finding that calls for action, then the watch items and settings.
- **3 Actions** — fish commands for each action, one line each; every HIGH, MED, and LOW finding is answered by an action. A failed unit is looked up in its own boot and manager (`journalctl -b -1`, `--user-unit`) by its name as logged, a masked identifier as `*`, and a name too long for the line keeps its ends around a `*`. Kernel errors are looked up in the warning-level kernel journal with monotonic times. The ry-verify rerun calls the script by the absolute path its log's header records, else `~/ry-verify/ry-verify.fish`, after `sudo -v` when sudo stopped the run or its cache lapsed. A ry-verify log from another machine, installation, or boot gets that rerun alone, as the first action, with a note to capture the bug report again after a reboot. Above a paired log's rerun stand up to 6 of ry-verify's own suggestions in log order — the `↳` line under a FAIL, WARN, or ERR record, quoted without the arrow; an INFO record naming a `Run:` or `Install missing:` command; a FAIL or WARN record whose last clause names its fix (`— sudo chown …`, `— … until sudo systemctl restart …`), cut from its start when too long — and the checks a lapsed sudo cache skipped. A finding no failure action answers gets its rule's task: a unit that failed under a redacted name is searched for in its own boot and manager (`journalctl -g 'Failed with result'`), the Wi-Fi P2P device's state is read with `nmcli` after a NetworkManager restart, a HID joystick's vendor and product IDs, up to 6, are listed as `SDL_GAMECONTROLLER_IGNORE_DEVICES` takes them, above a check of the session environment, and jack2 is replaced through `pacman`. An action without commands points at its finding's card.
- **4 System health** — the ry-verify result (named as another machine's or boot's when a pairing check differs), the hardware checks, and the CPU scheduler the bug report's scheduler section names (BORE with its version, sched_ext with its state or loaded scheduler), each with its result, detail, and source; the lines each error class matched in dmesg and in each journal boot.
- **5 Boot** — the boot chart and boot activity by subsystem, the milestones and captures with the step between them, and the longest pauses in dmesg during the boot's burst.
- **6 dmesg** — each subsystem's lines per boot phase and after the boot (its first and last line once dmesg has lost the boot), its lines with failure keywords, and the rules they match; the chart and the messages after the boot; the sources with failure keywords; and repeated warnings, one sentence when every line of them comes after the boot and the after-boot table lists them.
- **7 Journal** — an overview per boot, the timeline, entries by process, repeated warnings, the messages new in the current boot, and the unit failures systemd logged.
- **8 ry-verify** — results by section, failures and warnings grouped by section, and notes; a log from another machine, installation, or boot opens the section with a sentence that says where it comes from.
- **Appendices** — A: the INFO findings, each with what it means. B: both inputs with their full SHA256, the parser cross-checks, and the method.
- **Every page** — the footer names the generator, the capture date, and the first 8 hex digits of each input's SHA256; past the cover, the running header names the machine (a name too long to leave the counts room is cut), the HIGH, MED, and LOW counts, and the section. Severity marks, drawn as shapes, stand beside the levels in the counts, the register, and the contents: a filled square for HIGH, a half-filled one for MED, an open one for LOW.
- **The file** — the PDF opens with its bookmarks shown, names the machine and capture date in its title, states its language, and carries both inputs as compressed attachments, byte for byte and unmasked, unless `--no-attach` leaves them out.

A log section without content is one sentence, and a journal whose lines could not be read adds its overview table; a journal boot of which no line could be read counts as not read, never as zero. The ry-verify failures table lists 20 rows per section, the notes and unit-failure tables 40 rows, and a last row counts the rest by line; in the failures table, 3 or more records of one section that share a status and the text after their first `: ` (`nvme-cli: NOT INSTALLED`) or before it (`File NOT FOUND: …`) are one row: the shared part, the count, and the parts that differ. A word too wide for its column, in a table cell or an Appendix A note, breaks after a slash or another separator instead of mid-name.

Quotes keep their line numbers: BR, a line of the bug report; VJ, a line of the ry-verify log, blank lines counted. A quote from wrapped inxi output shows the line its number names. Identifiers in quotes and in ry-verify section names (UUIDs, machine and USB4 domain IDs, serials, MAC, IPv4, and IPv6 addresses, home directories, email addresses) are replaced by placeholders such as `[root UUID]` and `[serial]`. ANSI escapes are removed; other control characters (tab and line feed aside), the Unicode line and paragraph separators, and invisible format characters (directional overrides and isolates, zero-width spaces, the byte order mark) show as U+FFFD, as do the bytes of a file name that are not UTF-8. A quote stops at 400 characters, as does a fact the cover or the health table states (a firmware version, a scheduler's name); a ry-verify version, profile, or mode stops at 40 and a section name at 60; a card quotes up to 8 lines, and a Lines cell lists up to 40 line ranges per log and counts the rest.

## How It Works

- **Bug report** — split at the separator lines `cachyos-bugreport.sh` writes, with or without blanks at their end, each section known by its title in any case (cachyos-settings 1.4.2 lowercases two); dmesg, both journal boots, inxi, and the package list are read line by line, numbered at newline characters only, as `rg -n` numbers them. inxi output in IRC form, which inxi prints when its stdin is not a terminal, reads like terminal output. The capture time comes from the `date` line in the C locale or any English locale glibc ships; in another language it is left unstated. Journal entries carry no year: each takes the latest year that puts it at most a day after the capture time (the ry-verify start when that is unstated), so an entry logged just after the capture and a boot across New Year both date right. A capture or ry-verify date outside 1970 to 9998 counts as unstated. Journal lines the parser cannot read (another locale's month names, say) are counted in the cross-checks and named wherever journal entries are counted.
- **ry-verify log** — the header, footer, phases, sections, and every OK, INFO, WARN, FAIL, and ERR record. As ry-verify counts them, ERR is a FAIL and a generator failure, logged as FAIL, a GEN_FAIL; phase banners, the notice a signal logs, and the ERR lines ry-verify does not count (continuations, and the sudo and boot-path notes older releases log as ERR) are no results, and the hardware-mismatch warning is no finding. A VERIFY_RESULT record belongs to the phase its `scope=` names (7.258.0), else to the phase it closes. The totals come from a footer that counts every record — a finished run's, or an interrupted one's from ry-verify 7.257.0 — else from the combined record, else from the phase records plus the records of a phase without one; preamble records the totals leave out are named. A run or phase whose records are all ERR, INFO records aside, stopped at a gate before its checks. The result reads in the words of ry-install's verdict: PREFLIGHT for exit 3; FAIL for a counted FAIL or GEN_FAIL, and for a failing exit the counts do not explain; else PASS-WITH-WARNINGS or PASS. An interrupted run reads interrupted, and a log without a footer or an exit code unknown. ry-verify's root UUID (`ROOT_UUID_OK`) stands in for one the bug report redacts. For the pairing checks (Cross-checks, below), the kernel release it ran on is read from `KERNEL_RELEASE` (logged from 7.265.0; `unknown` names none), and the CPU its hardware gate detected from the mismatch warning, else from `HARDWARE_MATCH` (logged from 7.251.0). When a pairing check differs, the log comes from another machine, installation, or boot and says nothing of the captured one: its FAIL, GEN_FAIL, and WARN records make no findings, its OK records lower none, and none is cited. One LOW finding takes their place, titled by the first difference, with the record that shows each difference as its evidence; the register links it to Section 8, the verdict names it with the first difference, the key facts name each, and its action reruns ry-verify. A footer count or exit code that is not a whole number from 0 to 999,999,999 is an input in the wrong format. Both inputs are read as UTF-8, with or without a byte order mark; blank lines in the JSONL log are skipped.
- **Rules** — each rule names a message class: where it appears, the patterns that recognize it, its severity, what it means, and what to do; the first matching rule claims a line. The rules read the first 4,096 characters of a dmesg line or journal entry, four times the kernel's longest record, which bounds what a line stuffed with one rule's keywords costs. A rule with context patterns also claims the other lines of the same event: within 3 lines after a line it claims, from the same source, a line no rule matches that a context pattern does (the ring-reset lines after a GPU timeout), or a lead pattern while the last line claimed is the rule's own match (the timeout's line naming the process; a later page fault prints one too). A rule that cites ry-verify quotes its last record about the same setting, whatever its status (the driver's ASPM setting beside Wi-Fi firmware timeouts). A ry-verify OK record that shows a finding's mitigation lowers it to INFO and is cited, unless a FAIL, GEN_FAIL, or WARN record about the mitigation contradicts it, the record and the sub-heading above it leave out a device the evidence comes from (named by its USB vendor and product IDs), or the evidence names no device. A log that a pairing check shows comes from another machine, installation, or boot is not cited and lowers no finding (ry-verify log, above). A rule limited to the shutdown window matches the previous boot's entries within 15 s of its last one when those hold a line only a stop sequence logs, as the capture keeps only warnings and worse.
- **Subsystems and sources** — a dmesg line belongs to the subsystem its wording names (a DRM error, an I/O error, an OOM kill, a hardware error, a kernel splat with its banner and register dump, and common boot lines such as keyrings, serial ports, NUMA, and traffic control), else to the one its prefix names (a driver, facility, or device), else to Other; an indented line belongs to the message above it. A line's source is the text before its first colon and space when that is at most 40 characters and three words (a driver and its device, such as `usb 1-4`, an interface, or a subsystem), else its first word; an indented line takes the source of the line above, and kernel splats, OOM kills, machine checks, block-layer and file-system errors, and DRM function tags have sources of their own. The source table lists 10 sources: those of findings that call for action first, then those no rule explains, then explained ones, each group by its lines with failure keywords. A journal entry belongs to the process that logged it.
- **Failure keywords** — 53, matched case-insensitively as whole words: `fail` · `failed` · `failure` · `failures` · `error` · `warn` · `warning` · `unable` · `cannot` · `can't` · `could not` · `couldn't` · `not supported` · `unsupported` · `not found` · `no such` · `denied` · `invalid` · `timeout` · `timed out` · `abort` · `aborted` · `aborting` · `crash` · `crashed` · `panic` · `oops` · `bug` · `taint` · `taints` · `tainting` · `call trace` · `segfault` · `fault` · `faults` · `io_page_fault` · `killed` · `refused` · `reset` · `hang` · `lockup` · `stall` · `stalls` · `corrupt` · `corrupted` · `corruption` · `mismatch` · `deprecated` · `unknown` · `lacking` · `kaput` · `critical temperature` · `hardware protection`.
- **Counts** — counts are of messages: a continuation belongs to its entry. Lines and entries with a failure keyword are counted per log, boot, subsystem, source, and process, those a NOTE rule claims aside. Repeated warnings group messages whose text differs only in numbers and hex values after the first word, which names the driver or device, while placeholders keep their own digits: dmesg lines with a failure keyword, boilerplate aside, and every journal entry, as the capture keeps warnings and worse; each table lists the 10 most frequent. The messages after the boot group the same way, in order of their first line, the first 10; the boot comparison lists the current boot's messages the previous boot did not log, numbers and hex values aside, the 10 most frequent. A message logged once is quoted as logged, repeats as their template.
- **Boot** — the kernel runs until it starts init (`/init` when an initramfs holds it), the initrd until the switch to the root file system, and userspace until the boot's burst of dmesg lines ends; a phase dmesg does not bound is left out. The switch is systemd's `Switching root` line where dmesg holds it; systemd logs that line to the initrd's journald, so dmesg seldom does, and the stop of that journald (`Received SIGTERM`) stands in when systemd's start banner follows it. The burst ends at the first 30 s pause after the last milestone: one within 600 s of the kernel start, or a later start of init, root mount, or root switch, as after a long wait for a disk passphrase. Its window runs 600 s from the kernel start, or from such a later milestone; without a pause in it, the burst ends at the window's last line, cut, and userspace lasts at least its span (≥). A ring buffer whose first line comes more than a second after the kernel start has lost the boot: the boot charts, phases, milestones, pauses, and the lines after the boot are left out, and Section 5 says where dmesg starts.
- **Kernel start** — each kernel message logged once in both dmesg and the current journal bounds the start to the second the journal stamps, and the estimate is the middle of the window they share; a message printed while no journald ran (before the first one's first line in dmesg, or between the stop of the initrd's and the first line of the root's) bounds it from above only, as journald stamps it when it reads it, and messages after the first suspend are left out, as dmesg time stops while the system sleeps.
- **Figures** — five, in grayscale: the boot chart (dmesg lines per bar, 0.01 to 5 s wide by the span shown, with the longest silence before the root mount, a band of the boot phases with their durations in the legend, the milestones, and the captures); boot activity by subsystem (one tick per line from each subsystem's first line to its last, aligned under the boot chart); dmesg after the boot (one tick per line after the burst, one row per subsystem, in seconds, minutes, or hours by the span shown, with a dashed line at each suspend); the journal timeline (entries per bar for each boot, on a log scale once a bar holds 20, above a tick per second with an entry a rule matches, one row per finding or message class; the current boot timed from the kernel start when it can be estimated, in seconds, minutes, or hours by its span, the previous boot by the wall clock); and ry-verify results by section (the static phase above the runtime phase, on one scale). They and the cover's uptime strip stripe a bar where two grays would sit close (the initrd phase and WARN black on white, GEN_FAIL white on black), as SVG patterns do not survive the conversion. The boot chart covers the burst and the captures up to twice its length, within 600 s of the kernel start; its caption names a cut, the milestones past the chart, and the dmesg lines it leaves out. A ry-verify run that starts on the chart is drawn as a bar to its edge, and a capture later than the chart or before the kernel start appears in the timeline table only. The run of a ry-verify log that a pairing check shows comes from another machine, installation, or boot is placed on no chart and not on the uptime strip: the timeline table lists it by its wall clock alone, and the boot chart's caption names it. Past 2,000 lines, ticks that would print as one are drawn once. A figure without data is left out and its section says so.
- **Cross-checks** — in Appendix B.2: ry-verify's per-phase counts against its result records, its combined totals against its footer, and its records, the preamble's too, against a footer that counts them all; a finished run's exit code against its counts, 1 with a FAIL or GEN_FAIL and else 0, as ry-verify sets it (a gate's exit 3 and an interrupted run aside); the pairing checks, each where both logs state the fact: the CPU vendor ry-verify detected against inxi's, its root file system against the bug report's (cachyos-settings 1.4.2 and later redact the bug report's UUIDs), its kernel release against the bug report's (inxi's, else the `uname:` line's; a placeholder `cachyos-bugreport.sh` wrote into the release stands for any text), the kernel command line tokens it checked against the bug report's `cmdline:` line (a token it found is not held against a line with a redacted token other than `root=`), and its start against the kernel start, as a run from before the captured boot describes an earlier one (not when the bug report's own capture time lies before that kernel start: the clock was then set back since the boot, as when daylight saving time ends, and a start before it shows nothing); every journal line as an entry, a continuation, a marker, or an unread line; the kernel messages paired between dmesg and the journal, which must agree on the kernel start; and the 7 sections `cachyos-bugreport.sh` writes.
- **Reproducible** — the same inputs under the same file names, with the same fonts, library versions, and zlib, give a byte-identical PDF in any directory and under any output name, dated by the capture time (else the ry-verify start) unless `SOURCE_DATE_EPOCH` is set, and so does the JSON summary; no `matplotlibrc` applies. A capture time whose date line names its zone only by abbreviation takes the ry-verify log's UTC offset when both fall on the same day.

## Adding Rules

Add an entry to `RULES`: key, title, area, severity (HIGH, MED, LOW, INFO, WATCH, SETTING, or NOTE), streams, patterns, and explanation (an empty one leaves the card's row out), plus an action unless none is needed. Optional fields limit a rule to the previous boot's shutdown window (`window="shutdown"`), to certain processes (`idents`), or to hardware named in the bug report (`requires`), or let a ry-verify record mark it mitigated (`mitigated_by`), and with `covers="ids"` require that record to name each device by its USB vendor and product IDs; `context` claims the other lines of one event, `lead` such a line only while the last line claimed is the rule's own match, and `cites` quotes ry-verify's record about the same setting. A HIGH, MED, or LOW rule that no failure action covers names its checklist action (`task`) and that action's completion test (`done`); a function under the rule's key in `RULE_COMMANDS` builds the commands from the finding's evidence, and a finding whose rule names no task still gets an action, which points at its card.

## JSON Summary

`--json PATH` writes the run as JSON in ASCII, other characters escaped, schema 1: `schema`, `generator`, `day` and `captured`, `machine`, `kernel`, the `inputs` with their file names, bytes, and SHA256, `ry_verify` (version, profile, mode, result in the report's words, exit as text, exit_code as a number or null, totals), the `findings` (ID, rule key, severity, title, first line, and the evidence lines counted per log and journal boot; a ry-verify log from another machine, installation, or boot is the one finding under the key `verify-pairing`), the `watch` items and settings, and the `actions` with their IDs, titles, the findings they answer, and completion tests. `--compare` reads `schema`, `day`, `generator`, and `machine`, and each finding's `id`, `key`, `severity`, and `title`; IDs are renumbered each run, so findings match by `key`.

## Verify

```fish
sudo pacman -S --needed poppler ruff ty
set -l vj (path sort ~/ry-install/logs/*/verify-*.jsonl)[-1]
./build_report.py --bugreport cachyos-bugreport.log --verify $vj --check
./build_report.py --bugreport cachyos-bugreport.log --verify $vj --out /tmp/a.pdf
./build_report.py --bugreport cachyos-bugreport.log --verify $vj --out /tmp/b.pdf; and cmp /tmp/a.pdf /tmp/b.pdf; and echo reproducible
pdffonts /tmp/a.pdf
pdfdetach -list /tmp/a.pdf
ruff check build_report.py; and ruff format --check build_report.py; and ty check build_report.py
```

Every `pdffonts` row shows `yes` in its `emb` column, and `pdfdetach` lists the two inputs. `ruff` reads `ruff.toml`; `ty` needs no settings but resolves imports in the system Python, so it needs the pacman packages of Quick Start, and after the `uv run` route alone it reports them unresolved.

## Requirements

- Python 3.12 or newer; tested on 3.12, 3.13, and 3.14, which build the same PDF, byte for byte where they link the same zlib (zlib-ng compresses it to other bytes)
- ReportLab 5.1.0, matplotlib 3.11.2, svglib 2.3.2 and 2.4.0, and Pillow 13.0.0 as tested; the script metadata requires at least ReportLab 5.0, matplotlib 3.11, svglib 2.2, and Pillow 12, which on Python 3.12 build the same PDF
- IBM Plex TTF files, the 9 named at the top of the script; `ttf-ibm-plex` on Arch, `fonts-ibm-plex` on Debian
- Inputs from `cachyos-bugreport.sh` (cachyos-settings 1:1.4.1-1 as tested; the layout and redactions of 1.4.2 to 1.4.4 and of the CachyOS-Settings tree after them, as the script writes them) and ry-verify 7.265.0 as tested
- To run the Section 3 commands: fish, and systemd's `systemctl`, `journalctl`, and `coredumpctl`; the Wi-Fi P2P task also runs NetworkManager's `nmcli`, and the jack2 task `pacman`
- To lint: ruff 0.17.5, and ty 0.0.101 and 0.0.102, as tested
- Quick Start and Verify run as written on Arch Linux with its own packages (Python 3.14, fish 4.9), all but `cachyos-bugreport.sh`, which CachyOS's `cachyos-settings` ships
